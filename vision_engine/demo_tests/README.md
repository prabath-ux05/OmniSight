# Vision Engine Live Validation

## Purpose

This directory contains a controlled local webpage used to validate the
OmniSight Vision Engine with the Gemini Vision-Language Model provider.

The demo includes three isolated scenarios:

- Clean page: expected to produce no findings.
- Text overflow: expected to produce a `layout_overflow` finding.
- Broken image: expected to produce a `broken_image` finding.

**Note:** This is a controlled test fixture, not the team's actual demo website.

## Prerequisites

- Python 3.12
- Project virtual environment activated
- Gemini API key configured as `GEMINI_API_KEY` in the root `.env` file
- Playwright and Chromium installed

Install Playwright if necessary:

    python -m pip install playwright
    python -m playwright install chromium

## Capture browser evidence

From the repository root:

    python -m vision_engine.demo_tests.capture_evidence

The command creates screenshots and HTML snapshots in `evidence/`.

## Run live Gemini validation

Run screenshot-only and DOM-only tests:

    python -m vision_engine.demo_tests.run_gemini_tests

Run DOM-only timeout diagnostics:

    python -m vision_engine.demo_tests.run_dom_timeout_check

The diagnostic uses a 60-second configured request timeout.

## Screenshot cropping benchmark

The separate benchmark compares three screenshot-analysis modes:

    python -m vision_engine.demo_tests.benchmark_crop_modes

The benchmark evaluates two defect scenarios using the Gemini provider:

- Full-image: sends the original screenshot.
- Single-crop: sends one cropped defect-region image.
- Multi-crop: sends two cropped images, one defect-region crop and one context crop.

### Latest benchmark results

| Scenario | Mode | Expected defect detected | Time |
|---|---|---:|---:|
| Overflow | Full image | Yes | 7.370 s |
| Overflow | Single crop | Yes | 6.305 s |
| Overflow | Multi-crop | Yes | 13.199 s |
| Broken image | Full image | Yes | 5.144 s |
| Broken image | Single crop | Yes | 5.464 s |
| Broken image | Multi-crop | Yes | 13.006 s |

All six benchmark runs succeeded, and all six detected the expected defect.

### PNG payload comparison

| Scenario | Full image | Single crop | Multi-crop |
|---|---:|---:|---:|
| Overflow | 17,157 bytes | 6,810 bytes | 14,958 bytes |
| Broken image | 17,792 bytes | 7,432 bytes | 15,365 bytes |

Single-crop analysis reduced the PNG payload by approximately 60.3% for
overflow and 58.2% for the broken-image scenario.

### Interpretation and limitations

- Single-crop analysis retained the expected detections in both scenarios.
- Multi-crop analysis also detected both defects but took longer because it
  uses two image-analysis requests per scenario.
- Single-crop analysis was slightly faster on average than full-image
  analysis in this individual benchmark.
- The crop coordinates are fixed approximate regions for the controlled
  test screenshots.
- The benchmark covers only two defect scenarios and one run per mode.
- These results do not establish general detection accuracy, API cost savings,
  or statistically reliable performance improvements.
- PNG payload size is not equivalent to billed API cost or token usage.

The benchmark writes its results to:

    evidence/crop_comparison_results.json

It does not overwrite the existing live-validation report.

## After-repair verification

The Vision Engine includes after-repair verification support with these
outcomes:

- `resolved`: no matching finding remains.
- `partially_resolved`: all matching findings have lower severity.
- `unresolved`: at least one matching finding remains at the original
  severity or a higher severity.
- `unverifiable`: the after-repair evidence cannot be validated.

Regression tests cover mixed-severity findings to ensure a repair is not
marked partially resolved when a finding remains at the original severity.

## Validation notes

The Gemini provider was tested with the `gemini-3.5-flash-lite` model.

The previously recorded six-test live validation run reported:

- Six successful requests and zero failed requests.
- All three screenshot-only scenarios matched expectations.
- All three DOM-only scenarios matched expectations.

That run's response times ranged from 4.913 to 103.730 seconds.
Live API response times can vary; these are individual observations.

The latest recorded crop benchmark separately completed six successful runs
with all six expected defect detections.

Run the current tests before reporting a test count. Historical test counts
in older reports may not reflect the current code.

The controlled local fixture does not replace validation against the team's
actual demo website. That requires the team's demo URL and suitable access.

## Security

Never commit the root `.env` file or expose Gemini API keys in test reports.
